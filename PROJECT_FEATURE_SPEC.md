# PROJECT FEATURE SPECIFICATION

## 1. Project Overview

This project is a server-rendered PHP time-tracking application for recording work hours against construction sites or work locations ("projects" / "Baustellen"). It is designed for simple webspace deployment without a framework and can run on either SQLite or MySQL/MariaDB through PDO.

Primary user groups:

* Administrators who set up the system, create users, create or rename projects, assign projects to users, backfill time entries, edit existing time entries, review monthly totals, and export CSV reports.
* Employees who log their own work time for the current day, see their assigned projects, view their monthly history, and change their password.
* Trainees, who behave the same as employees from a permissions perspective but are labeled separately in reporting and user management.

Core use cases:

* Initial bootstrap by creating the first admin account.
* User login and logout with session-based authentication.
* Assignment of users to projects before time can be booked.
* Entry of work time with start time, end time, break, project, and optional note.
* Monthly review of recorded hours for users, admins, and projects.
* CSV export of monthly totals, user detail rows, and project detail rows.

Overall system scope:

* Single-site monolithic web application.
* No separate frontend build, service layer, REST API, or background worker.
* All business logic is implemented directly in PHP page controllers and shared bootstrap helpers.

## 2. High-Level System Architecture

Frontend technologies:

* Server-rendered HTML generated by PHP files.
* One shared stylesheet in `style.css`.
* Minimal inline JavaScript in `dashboard.php` and `admin_time_entry.php` to combine hour and minute dropdowns into hidden `HH:MM` form values.
* Responsive layout using CSS media queries for screens `<= 640px`.

Backend technologies:

* Plain PHP 8 style application with shared bootstrap in `init.php`.
* Shared page rendering helpers in `view.php`.
* Native PHP sessions for authentication state.
* Native password hashing via `password_hash()` and verification via `password_verify()`.

Database technologies:

* PDO is the only database access layer.
* SQLite is the default deployment mode, storing data in `data/stundenerfassung.sqlite`.
* MySQL/MariaDB is supported through DSN configuration.
* Schema creation and lightweight migration happen automatically inside `init.php::migrate()`.

APIs:

* There is no JSON API.
* The system exposes browser-oriented PHP routes that return HTML pages, redirects, or CSV file downloads.

External services:

* PDO drivers (`pdo_sqlite` or `pdo_mysql`) are required runtime integrations.
* Browser cookies are used for theme preference persistence.
* Browser-managed PHP session cookies carry authentication state.

File storage systems:

* SQLite file storage under the runtime `data/` directory.
* No uploaded files, object storage, or document storage exist.

Authentication mechanisms:

* Session-based login using a `user_id` stored in `$_SESSION`.
* Admin authorization via `role === 'admin'`.
* CSRF tokens for authenticated POST forms.
* User activity filtering via `active = 1` on user lookup and login.

Component interaction:

* A browser requests a PHP route.
* The route includes `init.php` directly or indirectly through `view.php`.
* `init.php` loads configuration, starts the session, opens the database lazily through `db()`, ensures database prerequisites, and runs schema creation or role migration.
* Route-level guards (`require_login()`, `require_admin()`, `verify_csrf()`) enforce access rules.
* Each route executes SQL directly through PDO.
* `view.php` renders a shared header, nav, flash messages, and footer for HTML pages.
* Some routes return CSV directly instead of HTML when `export` query parameters are present.

## 3. Repository Structure

Important paths:

* `/`  
  Application root. All PHP routes, shared bootstrap code, stylesheet, SQL reference schema, and documentation live directly in the repository root. There is no nested `frontend/`, `backend/`, or `api/` directory split.

* `/data`  
  Runtime-generated directory for the SQLite database file. It is not committed, but the application will create the directory automatically for SQLite if possible. `.gitignore` excludes `data/*.sqlite`.

* `init.php`  
  Core bootstrap and shared runtime layer. Handles configuration loading, timezone, session startup, database connection, schema creation, role migration, startup error rendering, authentication helpers, CSRF helpers, flash messaging, theme persistence, and time utility helpers.

* `view.php`  
  Shared presentation wrapper. Renders the HTML shell, navigation, flash messages, and footer.

* `config.php`  
  Environment configuration for app name, timezone, DSN, DB credentials, and session cookie name.

* `schema.sql`  
  Reference schema file for the SQLite data model. The runtime source of truth is still `init.php::migrate()`.

* `style.css`  
  Entire UI styling layer, including light theme, dark theme, layout, tables, buttons, flash styles, and mobile responsiveness.

* `README.md`  
  Human deployment and usage documentation for webspace setup, SQLite/MySQL configuration, admin areas, dark mode, mobile optimizations, and time-entry rules.

Route files by responsibility:

* Authentication and bootstrap routes: `index.php`, `login.php`, `logout.php`, `setup.php`
* Employee self-service routes: `dashboard.php`, `time_entry_save.php`, `user_settings.php`, `user_change_password.php`, `theme_toggle.php`
* Admin navigation and management routes: `admin.php`, `admin_users.php`, `admin_save_user.php`, `admin_update_user.php`, `admin_projects.php`, `admin_save_project.php`, `admin_assign_projects.php`, `admin_time_entry.php`, `admin_update_time_entry.php`, `admin_totals.php`, `admin_employee_details.php`, `admin_project_details.php`
* Legacy compatibility route: `report.php`

## 4. Data Model

Entity: User

Purpose:

* Represents every authenticated person in the system, including admins, employees, and trainees.

Fields:

* `id` - integer primary key
* `name` - display name
* `email` - unique login identifier, normalized to lowercase on save in admin flows
* `password_hash` - hashed password
* `role` - one of `admin`, `employee`, `trainee`
* `active` - integer/boolean-like enabled flag, default `1`
* `created_at` - creation timestamp

Relationships:

* Many-to-many with `Project` through `UserProject`
* One-to-many with `TimeEntry` as `user_id`
* One-to-many with `TimeEntry` as `created_by_user_id`

Where it is used in code:

* Authentication lookup in `login.php`
* Current session user lookup in `init.php::current_user()`
* First admin creation in `setup.php`
* Admin user creation and update in `admin_save_user.php` and `admin_update_user.php`
* Reporting in `admin_totals.php` and `admin_employee_details.php`
* Assignment UI in `admin_projects.php`
* Time-entry admin forms in `admin_time_entry.php`

Entity: Project

Purpose:

* Represents a worksite or work category that users can be assigned to and book time against.

Fields:

* `id` - integer primary key
* `name` - unique project name
* `active` - integer/boolean-like enabled flag, default `1`
* `created_at` - creation timestamp

Relationships:

* Many-to-many with `User` through `UserProject`
* One-to-many with `TimeEntry`

Where it is used in code:

* Employee project dropdown in `dashboard.php`
* Admin project create/rename in `admin_save_project.php`
* Admin assignment matrix in `admin_projects.php`
* Admin monthly project detail reporting in `admin_project_details.php`
* Admin time-entry create/edit form in `admin_time_entry.php`

Entity: UserProject

Purpose:

* Join table that determines which users are allowed to book time for which projects.

Fields:

* `user_id` - foreign key to `users.id`
* `project_id` - foreign key to `projects.id`

Relationships:

* Belongs to one `User`
* Belongs to one `Project`
* Composite primary key on `(user_id, project_id)`

Where it is used in code:

* Employee dashboard project list query in `dashboard.php`
* Assignment save logic in `admin_assign_projects.php`
* Assignment display logic in `admin_projects.php`
* Time-entry validation in `time_entry_save.php` and `admin_update_time_entry.php`

Entity: TimeEntry

Purpose:

* Stores a booked work interval for a user on a specific date and project.

Fields:

* `id` - integer primary key
* `user_id` - user who performed the work
* `project_id` - assigned project worked on
* `work_date` - work date
* `start_time` - start time in `HH:MM`
* `end_time` - end time in `HH:MM`
* `break_minutes` - break duration in minutes
* `notes` - optional free-text note
* `created_by_user_id` - user who created the entry
* `created_at` - creation timestamp

Relationships:

* Belongs to one `User`
* Belongs to one `Project`
* Belongs to one creator `User`

Behavioral constraints enforced in code:

* Start and end times must be quarter-hour values: `00`, `15`, `30`, `45`
* `end_time` must be after `start_time`
* `break_minutes` must be less than the entry duration
* The target user must be assigned to the selected project
* Entries for the same user and date may not overlap
* Non-admin users are forced to save only for themselves and only for the current day

Where it is used in code:

* Creation in `time_entry_save.php`
* Update in `admin_update_time_entry.php`
* Employee monthly list in `dashboard.php`
* Admin monthly list and editing in `admin_time_entry.php`
* Totals and export logic in `admin_totals.php`
* User drilldown in `admin_employee_details.php`
* Project drilldown in `admin_project_details.php`

Entity: Session State

Purpose:

* Stores logged-in user ID, CSRF token, flash messages, and current theme for the active browser session.

Fields:

* `user_id`
* `csrf_token`
* `flash`
* `theme`

Relationships:

* References `User` through `user_id`

Where it is used in code:

* Session bootstrap in `init.php`
* Flash message helpers in `init.php` and `view.php`
* Auth guard functions in `init.php`
* Theme preference fallback in `init.php`

Entity: Theme Preference Cookie

Purpose:

* Persists selected UI theme across sessions and browser restarts.

Fields:

* `theme` - `light` or `dark`
* Cookie attributes - one-year expiry, path `/`, `HttpOnly`, `SameSite=Lax`, `Secure` only on HTTPS

Where it is used in code:

* Read in `init.php::get_theme()`
* Written in `init.php::set_theme()`
* Toggled through `theme_toggle.php`

Entity: Flash Message

Purpose:

* One-request status feedback system for success and error messages after redirects.

Fields:

* `type` - typically `success` or `error`
* `message` - rendered text

Where it is used in code:

* Set in almost every POST handler and some redirecting GET routes
* Rendered in `view.php::render_header()`
* Cleared by `init.php::get_flashes()`

## 5. Feature Inventory

### Feature: First-Run Admin Setup

Description: If no admin user exists, the application redirects most rendered pages to `setup.php`, where the first admin can be created with name, email, and password. Setup is disabled once at least one admin exists.
User Role: Unauthenticated installer.
Entry Points: `GET /setup.php`, `POST /setup.php`.
Files / Modules involved: `setup.php`, `init.php`, `view.php`, `config.php`.
Dependencies: `users` table, database bootstrap, password hashing, flash messages.

### Feature: Session Login and Logout

Description: Users log in with email and password. Successful login stores `user_id` in the session and redirects to the dashboard. Logout destroys the session and returns to the login page.
User Role: All active users.
Entry Points: `GET /login.php`, `POST /login.php`, `GET /logout.php`.
Files / Modules involved: `login.php`, `logout.php`, `init.php`, `view.php`.
Dependencies: `users` table, PHP session support, password verification.

### Feature: Shared Authenticated Layout and Navigation

Description: Authenticated pages render a common header with app title, dashboard link, conditional admin link, theme toggle link, profile link, and logout link. Flash messages appear above page content.
User Role: Logged-in users.
Entry Points: All pages rendered through `view.php`.
Files / Modules involved: `view.php`, `style.css`, `init.php`.
Dependencies: session user lookup, flash storage, theme preference.

### Feature: Theme Toggle with Persistent Preference

Description: Users can switch between light and dark theme modes. The selected theme is stored in both session state and a persistent cookie, then applied as a body class on all rendered pages.
User Role: Logged-in users.
Entry Points: `GET /theme_toggle.php?theme=light|dark`.
Files / Modules involved: `theme_toggle.php`, `init.php`, `view.php`, `style.css`.
Dependencies: authentication, cookies, session state.

### Feature: Employee Time Entry Creation

Description: Logged-in non-admin users can create time entries only for the current day. They must choose one of their assigned active projects and provide start time, end time, break minutes, and optionally a note.
User Role: Employee, trainee, admin if using the same save endpoint from admin UI.
Entry Points: Dashboard form posting to `POST /time_entry_save.php`.
Files / Modules involved: `dashboard.php`, `time_entry_save.php`, `init.php`.
Dependencies: authentication, CSRF, project assignments, `time_entries`, `projects`, `user_projects`.

### Feature: Quarter-Hour Time Selection UX

Description: Time fields are selected via separate hour and minute dropdowns restricted to quarter-hour increments. JavaScript synchronizes those dropdowns into hidden fields submitted as `HH:MM`.
User Role: Users entering or editing time.
Entry Points: Dashboard and admin time-entry forms.
Files / Modules involved: `dashboard.php`, `admin_time_entry.php`.
Dependencies: browser JavaScript, server-side `is_quarter_time()` validation.

### Feature: Personal Monthly Time History

Description: Users can filter their own entries by month, see each booked row, and view the calculated monthly total hours. The table shows date, times, break, project, note, and calculated duration.
User Role: Logged-in users.

Files / Modules involved: `dashboard.php`, `init.php`.
Dependencies: authentication, `time_entries`, `projects`, hour-formatting helpers.

Description: Users can view their name and email and change their password by supplying current password, new password, and confirmation. New passwords must be at least 8 characters.
User Role: Logged-in users.
Entry Points: `GET /user_settings.php`, `POST /user_change_password.php`.
Files / Modules involved: `user_settings.php`, `user_change_password.php`, `init.php`, `view.php`.

### Feature: Admin Area Landing Page

## 6. User Workflows

Workflow: Initial System Setup

1. A user opens the site before any admin exists.
2. `ensure_admin_exists()` redirects rendered pages to `setup.php`.
3. The installer enters name, email, and password.
4. `setup.php` validates non-empty fields and password length of at least 8.
5. A new admin row is inserted into `users`.
6. A success flash is set and the browser is redirected to `login.php`.

Workflow: User Login

1. A user opens `login.php`.
2. The route checks whether an admin exists; if not, setup is forced first.
3. The user submits email and password.
4. The email is trimmed and lowercased.
5. The system loads an active user by email and verifies the password hash.
6. On success, `$_SESSION['user_id']` is set, a welcome flash is created, and the user is redirected to `dashboard.php`.
7. On failure, an error flash is shown and the login form remains available.

Workflow: Employee Creates a Time Entry

1. The employee opens `dashboard.php`.
2. The page loads only the active projects assigned to that user through `user_projects`.
3. The user selects start and end quarter-hour values, break minutes, project, and optional note.
4. The form always submits the current date as a hidden `work_date`.
5. `time_entry_save.php` verifies CSRF, forces `targetUserId` to the current user, and forces `work_date` to today for non-admin users.
6. The system validates date format, quarter-hour times, positive duration, break less than duration, project assignment, and non-overlap with existing entries.
7. On success, a `time_entries` row is inserted with `created_by_user_id` equal to the logged-in user.
8. The employee is redirected back to the dashboard with a success flash.

Workflow: Employee Reviews Monthly History

1. The employee selects a month on the dashboard.
2. `dashboard.php` loads all entries for that user where `substr(work_date,1,7)` matches the selected month.
3. The page calculates total minutes in PHP and formats them as hours with two decimals.
4. The table renders each row with project name, note, and per-entry duration.

Workflow: User Changes Password

1. The user opens `user_settings.php`.
2. The form requires current password, new password, and confirmation.
3. `user_change_password.php` verifies CSRF, minimum length, and password confirmation.
4. The current password hash is checked against the logged-in user record.
5. On success, the password hash is updated and the user is redirected back to the profile page with a success flash.

Workflow: Admin Creates a User and Assigns Projects

1. The admin opens `admin_users.php` and creates a new employee, trainee, or admin.
2. The user is stored as active with a hashed password.
3. The admin opens `admin_projects.php`.
4. The admin selects the user from the assignment dropdown.
5. The page loads existing `user_projects` links and checks the matching project checkboxes.
6. The admin submits the assignment form.
7. `admin_assign_projects.php` deletes all previous assignments for that user and inserts the selected ones inside a transaction.

Workflow: Admin Backfills or Edits Time

1. The admin opens `admin_time_entry.php`.
2. For a new entry, the admin fills user, date, quarter-hour times, break, project, and note, then posts to `time_entry_save.php`.
3. For an existing entry, the admin clicks `Bearbeiten`, which reloads the page with `entry_id`.
4. The form is prefilled from the selected row and now posts to `admin_update_time_entry.php`.
5. The server validates date, times, duration, project assignment, and overlap rules.
6. On success, the record is inserted or updated and the admin is redirected back to `admin_time_entry.php`.

Workflow: Admin Reviews Monthly Totals and Exports

1. The admin opens `admin_totals.php` and optionally changes the month.
2. The page aggregates total minutes per active user across all roles.
3. The admin can open user details for a row or export all totals as CSV.
4. The admin can also export one user's detailed monthly rows as CSV from the same list.

Workflow: Admin Reviews Project Details and Exports

1. The admin opens `admin_projects.php`, filters or sorts the project list, and clicks `Details` on one project.
2. `admin_project_details.php` loads monthly entries for that project and calculates total hours.
3. The page preserves the previous project-list filters in its back link and CSV export link.
4. The admin can change the month or download a project-specific CSV file.

Workflow: Theme Toggle

1. A logged-in user clicks the theme link in the shared header.
2. `theme_toggle.php` reads the requested theme and writes it to session and cookie storage.
3. The user is redirected back to the referring page or the dashboard.
4. `view.php` applies the theme-specific body class on the next render.

## 7. Module System (if present)

This repository does not implement a dynamic plugin or module activation system. There are no installable modules, feature flags, tenant-specific packages, or runtime extension points.

The application is instead organized into fixed functional modules:

* Bootstrap and persistence module in `init.php`
* Shared view/layout module in `view.php`
* Authentication module in `login.php`, `logout.php`, `setup.php`
* Employee self-service module in `dashboard.php`, `time_entry_save.php`, `user_settings.php`, `user_change_password.php`
* Admin management module in all `admin_*.php` files
* Theming module in `theme_toggle.php` and `style.css`
* Reporting/export module in `admin_totals.php` and `admin_project_details.php`

Activation logic:

* Admin-only features are activated by `role === 'admin'`.
* Time booking eligibility for a project is activated by the presence of a `user_projects` row.
* Login availability for any user is activated by `active = 1`.
* Project visibility in booking dropdowns is activated by both assignment and `projects.active = 1`.

Module dependencies:

* Every functional module depends on `init.php`.
* All HTML modules depend on `view.php` and `style.css`.
* Reporting depends on time entry capture having already populated `time_entries`.

## 8. API Endpoints

The project exposes page-controller routes rather than a JSON API.

| Method | Route | Purpose | Authentication requirements | Response type |
| --- | --- | --- | --- | --- |
| GET | `/index.php` | Redirect to dashboard if logged in, otherwise to login | None | HTTP redirect |
| GET | `/login.php` | Render login form | None, but setup must already be complete | HTML |
| POST | `/login.php` | Authenticate by email and password | None | Redirect with flash |
| GET | `/logout.php` | Destroy session and log the user out | None beyond existing session | Redirect |
| GET | `/setup.php` | Render first-admin setup form when no admin exists | None | HTML |

## 10. Configuration and Environment

Important configuration mechanisms:

* `config.php`
  Defines `app_name`, `timezone`, `dsn`, `db_user`, `db_pass`, and `session_name`.

* Database DSN switching
  The application can run against SQLite by default or MySQL/MariaDB when the DSN and credentials are changed.

* Timezone
  `date_default_timezone_set()` is driven by `config.php`, defaulting to `Europe/Berlin`.

* Session naming
  The PHP session name is configurable and defaults to `stundenerfassung_session`.

* Runtime schema creation
  The application creates missing tables automatically from `init.php::migrate()` rather than relying on a separate deployment migration command.

* SQLite prerequisites
  `ensure_database_prerequisites()` creates the parent directory with mode `0775` and verifies writability before opening the SQLite database.

* Reference schema
  `schema.sql` documents the expected schema, but the executable migration logic in `init.php` is the authoritative implementation.

* Styling and layout
  `style.css` is loaded directly without preprocessing, bundling, or theming build steps.

* Deployment
  The repository is intended for direct upload to webspace or a simple PHP host. There is no Composer manifest, package manager, container definition, or CI deployment script in the repo.

* Ignore rules
  `.gitignore` excludes SQLite database files under `data/`.

Environment expectations:

* PHP runtime with PDO.
* Either `pdo_sqlite` or `pdo_mysql`.
* Writable filesystem permissions for the SQLite directory when using SQLite.

## 11. Background Jobs and Automation

There are no scheduled jobs, cron tasks, queues, workers, or standalone automation scripts in the repository.

The only automated behaviors are request-time automations:

* Database tables are auto-created when `db()` is first used.
* SQLite directory creation happens automatically for SQLite DSNs.
* `users.role` support for `trainee` is migrated automatically at runtime.
* Flash messages are automatically cleared after being read.
* Theme preference is automatically persisted when the toggle route is called.

There is no asynchronous processing. All exports, calculations, and validation happen synchronously within the HTTP request that triggered them.

## 12. Security Model

Authentication:

* Login is email and password based.
* Passwords are stored only as hashes.
* Only `active = 1` users can log in or be loaded as the current user.
* If the session references a user that is no longer active or missing, `current_user()` clears `$_SESSION['user_id']`.

Authorization:

* `require_login()` protects authenticated pages.
* `require_admin()` protects all admin pages and returns HTTP 403 with `Keine Berechtigung.` for unauthorized access.
* Employee and trainee users cannot access admin routes.
* Non-admin users cannot create entries for other users or other dates because `time_entry_save.php` overrides both target user and work date.
* Time creation and update both verify that the target user is assigned to the selected project.

Request protection:

* CSRF tokens are generated once per session and required for authenticated POST forms.
* Protected POST handlers include user creation, user update, project save, project assignment, time entry create, time entry update, and password change.
* Login is not CSRF-protected.
* Theme switching is a state-changing GET route and is not CSRF-protected.

Input validation:

* Time strings must match `HH:MM` and use quarter-hour minutes only.
* Dates are validated with regex.
* Password changes require current password and confirmation.
* Break minutes are clamped to non-negative integers and must be shorter than total duration.
* Project and user IDs are cast to integers.

Output protection:

* HTML output is escaped through `h()`.
* Flash messages and user-entered notes are escaped before rendering.

Token and cookie behavior:

* CSRF token is stored in session state.
* Theme cookie is `HttpOnly` and `SameSite=Lax`; `Secure` is set only when HTTPS is detected.

Permission limitations and missing controls:

* There is no granular permission system beyond admin vs non-admin.
* There is no account lockout, MFA, password reset flow, or audit log.
* There is no UI to disable users or projects even though `active` fields exist.
* Session ID regeneration on login is not implemented.

## 15. Risk Areas for Refactoring

* `init.php` is a central coupling point. Database connection, schema migration, auth helpers, CSRF, theme handling, flash messages, and utility functions all live in one file, so changes can have application-wide side effects.
* Business logic is embedded directly in page controllers. There is no service layer separating validation, persistence, and HTML concerns, which makes extraction or route restructuring risky.
* Schema creation in request flow is operationally sensitive. Refactoring startup or `db()` behavior can break first-run provisioning, SQLite directory creation, or runtime role migration.
* Time-entry validation is duplicated between `time_entry_save.php` and `admin_update_time_entry.php`. Diverging changes can easily create inconsistent create vs update rules.
* The SQL is written for both SQLite and MySQL using string dates, `substr()`, and integer casts. Query rewrites can accidentally break one engine while fixing the other.
* `current_user()` uses a static cache for the current request. Refactoring auth/session flow without noticing this cache can create stale user data behavior.
* `active` fields exist in schema and queries but are not manageable through the UI. Refactors that remove them may silently change login and reporting filters; refactors that expose them need careful UX and authorization design.
* Project detail pages preserve prior filter state through explicit query-string copying. Changing parameter names or link generation can break back-navigation and export continuity.
* Theme switching uses a state-changing GET route. Reworking routing or caching around it can produce surprising behavior or stale theme state.
* `report.php` is a compatibility alias. Removing it can break bookmarked or legacy links even though it no longer contains report logic.
* CSV export output depends on exact field ordering and semicolon delimiters. Refactoring response generation can break downstream spreadsheet imports.

## 18. Glossary

* App Name - Configurable display name shown in the header, default `Stundenerfassung`.
* Baustelle / Project - A worksite or project against which time can be booked.
* User - Any authenticated person in the system.
* Admin - A user with access to all management, reporting, and editing functions.
* Employee - A standard non-admin user who can enter only their own current-day time.
* Trainee - A non-admin user role with the same capabilities as employee but a separate label in management and reporting.
* Assignment - A `user_projects` relationship granting a user permission to book time on a project.
* Time Entry - One booked work interval with date, start time, end time, break, project, and optional note.
* Created By - The user who created a time entry; may differ from the worker when an admin backfills time.
* Monthly Totals - Aggregated total hours per user for a selected month.
* Project Details - A monthly report of all entries recorded against one project.
* User Details - A monthly report of all entries recorded for one user.
* Flash Message - A one-time status message shown after redirect.
* CSRF Token - Session-bound token required by authenticated POST forms.
* Theme Preference - User-selected light or dark mode persisted in session and cookie storage.
